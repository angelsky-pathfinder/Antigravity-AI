Designer가 확정한 KPI 카드 레이아웃과 시스템 안정성($S$) 및 수익 잠재력($SWRI$)의 대비 원칙을 기반으로, 백엔드 API에 필요한 최종 데이터 구조(Schema)와 연동 로직 요구사항을 설계하겠습니다. 데이터 흐름 안정성을 확보하는 것이 최우선입니다.

### 1. KPI 카드 데이터 스키마 설계 (Data Schema Specification)

KPI 카드는 동적인 상태를 반영하므로, 각 엔티티는 시간 기반의 시계열 데이터를 효율적으로 처리할 수 있도록 설계해야 합니다. 여기서는 핵심 지표와 그 계산 로직에 필요한 메타데이터를 정의합니다.

**엔티티명:** `KpiMetricData` (KPI 카드 데이터)

| 필드명 | 타입 | 필수 여부 | 설명 | 비고 |
| :--- | :--- | :--- | :--- | :--- |
| `kpi_id` | String (UUID) | 필수 | KPI 항목의 고유 식별자. | Primary Key |
| `metric_name` | String | 필수 | 측정 대상 지표명 (예: 'Injest Rate', 'Latency'). | |
| `timestamp` | DateTime | 필수 | 데이터가 측정된 정확한 시점. | Time-series index |
| `system_stability_s` | Float (0.0 ~ 1.0) | 필수 | 시스템 안정성 지표 ($S$). 신뢰도 기반 정규화 값. | Deep Blue 영역 결정 |
| `profit_potential_swri` | Float (0.0 ~ 1.0) | 필수 | 수익 잠재력 지표 ($SWRI$). 기회/위험 대비 정규화 값. | Crimson Red 영역 결정 |
| `derived_score` | Float (0.0 ~ 1.0) | 선택 | $S$와 $SWRI$를 결합한 최종 대비 점수. ($\text{Score} = f(S, SWRI)$). | 시각화의 핵심 축 |
| `status` | String | 필수 | 현재 상태 (예: 'Stable', 'Warning', 'Critical'). | 자동 분류 로직용 |
| `raw_data_reference` | String | 선택 | 원본 데이터의 참조 경로 (로그 파일, DB 레코드 ID 등). | 추적성 확보 |

#### 💡 스키마 설계 코멘트
$S$와 $SWRI$는 0과 1 사이로 정규화되어야 합니다. 이 값들이 단순한 측정값을 넘어 '시스템 안정성과 수익 잠재력의 대비'라는 **비즈니스 메시지**를 담도록, 최종적으로 `derived_score` 필드를 계산하는 로직이 중요합니다.

### 2. API 연동 초기 요구사항 (API Integration Requirements)

데이터 흐름 안정성($S$) 확보를 위해 API는 단순 데이터 반환을 넘어, **데이터의 유효성과 맥락(Context)**을 보장해야 합니다.

#### A. 엔드포인트 정의: `POST /api/v1/kpi/ingest`

이 엔드포인트는 모든 KPI 데이터를 시스템에 주입하는 핵심 경로입니다.

**요구사항:**
1.  **데이터 검증 (Validation):** 요청 본문(Payload)에 포함된 모든 필드(`kpi_id`, `metric_name`, `timestamp`, $S$, $SWRI$)가 정의된 스키마의 제약 조건($0 \le \text{value} \le 1.0$ 등)을 엄격하게 준수하는지 확인해야 합니다. **유효하지 않은 데이터는 즉시 거부하고 명확한 에러 코드(400 Bad Request)를 반환**해야 합니다.
2.  **맥락적 연동 (Contextual Linking):** 각 $S$ 및 $SWRI$ 값이 어떤 특정 시스템 상태나 외부 데이터와 연관되어 있는지(`raw_data_reference`)를 기록하여 추후 분석의 추적성을 보장해야 합니다.
3.  **원자성(Atomicity):** 하나의 요청에 포함된 모든 KPI 데이터 포인트가 성공적으로 저장되거나 실패해야 합니다 (트랜잭션 관리).

#### B. 연동 로직 요구사항: $S$와 $SWRI$의 계산 및 반영

백엔드 로직은 단순한 저장 이상의 역할을 수행해야 합니다.

1.  **정규화 로직 검증:** 입력된 $S$와 $SWRI$ 값이 시스템이 정의한 **'안정성 대비 수익 잠재력의 위험 지표'** 프레임워크 내에서 논리적으로 타당한지(예: $S=0.9, SWRI=0.1$은 매우 안정적이고 낮은 기회를 의미)를 검증해야 합니다.
2.  **`derived_score` 계산:** 시스템이 정의하는 핵심 가치에 따라 $S$와 $SWRI$를 결합하여 `derived_score`를 계산합니다. 이 계산 공식($f(S, SWRI)$)은 **절대적으로 고정**되어야 하며, 코드 레벨에서 명확히 정의되어야 합니다 (예: $\text{Score} = S \times (1 - SWRI)$ 또는 유사한 비즈니스 규칙 기반).
3.  **상태 자동 분류:** `status` 필드는 $S$와 $SWRI$의 임계값을 기준으로 자동으로 할당되어야 합니다 (예: $S < 0.5$ 이면서 $SWRI > 0.7$ 일 경우 'Critical'로 자동 설정).
