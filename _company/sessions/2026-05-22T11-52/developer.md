### 1. 애니메이션 구현 가능성 분석 (Feasibility Analysis)

제안된 모든 애니메이션은 **백엔드에서 실시간으로 제공되는 $S$와 $SWRI$ 값**에 직접적으로 종속됩니다. 따라서, 프론트엔드가 이 데이터를 구독하고 즉각적으로 반응하도록 설계한다면 기술적으로 구현 가능합니다.

| 애니메이션 유형 | 데이터 의존성 | 구현 난이도 | 코다리의 검토 의견 |
| :--- | :--- | :--- | :--- |
| **안정성 경고** ($S$ 감소) | $S$ 값의 변화 감지 (임계치 비교) | 중 | 백엔드에서 설정된 임계치($S_{threshold}$) 대비 현재 $S$ 값을 지속적으로 모니터링하고, 이 상태 변화를 WebSocket 또는 Polling을 통해 프론트로 전달해야 합니다. |
| **위험 경고** ($S$ 임계치 이하) | $S$ 값의 임계값 도달 여부 | 하 | 가장 즉각적인 피드백이 필요하므로, $S$ 값이 특정 시점에 도달하면 즉시 플래시 효과를 트리거하는 로직은 서버 측에서 결정하고 프론트로 상태만 전달하는 것이 효율적입니다. |
| **수익 과열 경고** ($SWRI$ 임계치 초과) | $SWRI$ 값의 변화 감지 | 중 | 이는 수익 극대화보다는 위험 관리에 집중되므로, 데이터 스트림에 따라 미세한 떨림 애니메이션을 적용하여 시각적 압박감을 주는 방식으로 구현 가능합니다. |

### 2. 기술적 제약사항 및 설계 고려사항 (Technical Constraints & Design Considerations)

애니메이션 구현 시 발생할 수 있는 잠재적인 문제점과 이를 해결하기 위한 제약을 아래와 같이 명시합니다.

#### A. 데이터 스트리밍 및 지연 시간 (Latency)
*   **제약:** 애니메이션의 효과가 데이터 변경으로부터 **지연 없이 즉각적**이어야 합니다. 만약 API 호출이나 데이터 파이프라인 처리에서 500ms 이상의 지연이 발생한다면, 사용자 경험은 심각하게 저하됩니다.
*   **해결 방안:** $S$와 $SWRI$의 실시간 변화를 위해 **WebSocket** 통신을 채택하여 서버에서 클라이언트로 푸시(Push)하는 구조를 설계해야 합니다. 이는 Polling보다 훨씬 효율적이며 낮은 지연 시간을 보장합니다.

#### B. 백엔드 로직의 책임 (Server-Side Responsibility)
*   **제약:** 시각 효과는 사용자 경험을 위한 것이지만, **실제 위험 판단 및 경고 발동 조건($S_{threshold}$, $SWRI_{threshold}$)은 반드시 서버에서 결정**해야 합니다. 프론트엔드는 이 조건을 단순히 받아 시각화만 담당합니다.
*   **해결 방안:** 모든 임계값과 상태 변화 로직은 `/api/metrics/realtime` 엔드포인트나 백엔드 서비스 레이어 내에 명확히 정의하고, 이 값이 최종 애니메이션 트리거의 **단일 진실 공급원(Single Source of Truth)**이 되도록 보장해야 합니다.

#### C. 성능 및 자원 관리 (Performance & Resource Management)
*   **제약:** 지속적인 실시간 데이터 스트리밍은 서버 리소스(DB 쿼리, API 호출 빈도)를 소모합니다. 특히 고빈도로 업데이트되는 지표는 백엔드 부하가 커질 수 있습니다.
*   **해결 방안:** $S$와 $SWRI$의 **업데이트 빈도를 적절히 조절**해야 합니다. 예를 들어, $S$ 값은 1초당 한 번, $SWRI$ 값은 5초당 한 번 업데이트하는 등, 사용자 인지 수준에 맞춰 데이터 스트리밍 빈도를 계층화할 필요가 있습니다.
