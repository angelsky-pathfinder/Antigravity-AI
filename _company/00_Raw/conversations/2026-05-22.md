## 2. 데이터 시각화 레이아웃 가이드라인 (Layout Guidelines)

### 2.1. 대시보드 구조 (Dashboard Structure)

대시보드는 크게 **상태 요약 섹션**, **핵심 지표 영역**, **시스템 상세 로그 영역** 세 부분으로 구성된다.

*   **상태 요약 섹션 (Top Banner):** 현재 시스템 안정성($S$)과 수익 지표($SWRI$)의 상태를 가장 큰 크기로 표시하여 즉각적인 상황 파악을 유도한다.
*   **핵심 지표 영역 (Metrics Core):** $S$와 $SWRI$를 중앙에 배치하고, 이들이 서로 어떻게 연결되는지를 시각적 흐름(Flow)으로 표현한다.
*   **시스템 상세 로그 영역 (Detail Log):** API 응답 상태($S$, $SWRI$)의 변화 추이 및 Circuit Breaker 상태를 시간 순서대로 표시하여 백엔드 로직의 신뢰성을 증명한다.

### 2.2. 핵심 지표 시각화 정의

#### A. 시스템 안정성 ($S$) 시각화 (System Stability)

*   **시각 요소:** 동적 게이지 바 (Dynamic Gauge Bar)
*   **색상 매핑:**
    *   $S \in [0.8, 1.0]$: Gold Accent (안정/최상)
    *   $S \in [0.5, 0.8)$: Deep Navy에 점진적 변화 (주의)
    *   $S < 0.5$: Crimson Red (위험/경고)
*   **애니메이션 규칙:** $S$ 값이 변경될 때, 게이지 바는 **Crimson Red $\rightarrow$ Gold Accent** 또는 **Gold Accent $\rightarrow$ Crimson Red**로 부드럽게 전환되어야 한다. (Transition: 500ms ease-in-out)

#### B. 수익 지표 ($SWRI$) 시각화 (Revenue Metrics)

*   **시각 요소:** 도넛 차트 및 라인 그래프 조합
*   **색상 매핑:**
    *   주요 수치 (Monthly Revenue): Gold Accent
    *   Conversion Rate: Deep Navy 배경 위에 Crimson Red으로 강조된 꺾은선 그래프로 표시.
*   **레이아웃:** $SWRI$를 중심으로 월별 추이 라인 그래프와 현재 달성치를 도넛 차트로 배치하여, **안정성($S$)이 수익에 미치는 영향**을 명확히 보여준다.

## 3. 애니메이션 및 상태 변화 가이드라인 (Animation & State Transition Rules)

모든 시각화는 사용자의 행동 변화를 유도하고 시스템의 신뢰도를 반영해야 한다.

### 3.1. Circuit Breaker 상태 애니메이션

| 상태 | 시각적 표현 | 애니메이션 규칙 | 설명 |
| :--- | :--- | :--- | :--- |
| **CLOSED** | Gold Accent (점) | 정적 표시 | 시스템이 정상 작동 중. |
| **OPEN** | Crimson Red (경고 아이콘 + 굵은 테두리) | 깜빡임 (Blink) | 요청 차단 상태. 사용자에게 즉각적인 조치를 요구함. |
| **HALF-OPEN** | Deep Navy 배경 위에 Gold Accent 점멸 | 느린 주기적 깜빡임 | 재시도 중. 시스템이 복구 과정을 거치고 있음을 알림. |

### 3.2. 데이터 로딩 및 업데이트 애니메이션

1.  **초기 로딩:** 전체 대시보드 로드 시, 배경은 Deep Navy로 서서히 나타나며 (Fade-in), 핵심 지표들은 Gold Accent 색상으로 점진적으로 채워진다 (Staggered Load).
2.  **데이터 업데이트:** API 응답이 수신될 때, 기존 데이터는 빠르게 페이드 아웃(Fade-out)되고 새로운 데이터는 부드럽게 페이드 인(Fade-in)되어야 한다. 이 과정에서 **Crimson Red** 색상은 데이터가 '갱신 중'임을 잠시 표시하는 데 사용된다.
3.  **경고 발생 시:** $S$ 또는 $SWRI$ 값이 임계치를 벗어날 경우, 해당 영역은 즉각적으로 Crimson Red로 플래시(Flash)되며, 애니메이션이 멈추지 않고 **3초간 지속**되어야 한다.

1.  **Color/Font:** Deep Navy, Gold Accent, Crimson Red 사용 및 Inter 폰트 적용.
2.  **Data Mapping:** $S$는 게이지 바로, $SWRI$ 추이는 라인 그래프로 시각화.
3.  **Interaction:** 모든 상태 변화(CLOSED, OPEN 등)는 확정된 애니메이션 규칙에 따라 즉각적으로 반영되어야 한다.
4.  **Resilience Focus:** Circuit Breaker의 **OPEN/HALF-OPEN** 상태를 Crimson Red 및 Gold Accent을 사용하여 명확하게 표시하여 시스템 안정성($S$) 확보가 최우선임을 강조한다.

### A. 상관관계 분석 단계 (Correlation Analysis)
1.  **데이터 연동:** 수집된 행동 로그 데이터, 경쟁사 모니터링 데이터, 거시 경제 데이터를 $S$와 $SWRI$의 시간 축과 정렬하여 시계열 분석을 수행합니다.

### B. 영향 가중치 산출 (Impact Weight Calculation)
가중치는 다음 공식을 기반으로 설정하여 위험 대비 수익 기회에 초점을 맞춥니다.

$$\text{Weight}(X \to Y) = \alpha \cdot |\rho_{X, Y}| + \beta \cdot \text{Risk\_Factor}(X)$$

*   $\rho_{X, Y}$: 변수 $X$와 지표 $Y$ 간의 상관관계 (데이터 기반).
*   $\text{Risk\_Factor}(X)$: 외부 변수의 잠재적 위험도 (예: 경쟁사 활동이 매우 높으면 Risk Factor 증가).
*   $\alpha, \beta$: 전략적 민감도 계수. ($S$에 대한 가중치 $\alpha$는 시스템 안정성 확보를 최우선으로 설정하고, $SWRI$에 대한 가중치 $\beta$는 수익 기회 포착을 반영합니다.)

### C. 최종 우선순위 결정 (Prioritization)

## 시스템 안정성($S$) 및 수익 지표($SWRI$) 영향 핵심 변수 분석 계획

### 1. 핵심 분석 변수 정의 (The 4 Core Variables)

다음 4가지 변수는 시스템의 내부 상태($S$)와 외부 환경(시장 반응) 간의 인과관계를 분석하는 데 가장 직접적으로 사용될 데이터입니다.

| No. | 핵심 변수 (Variable) | 목표 지표 연결 (Link to $S$ or $SWRI$) | 주요 측정 대상 |
| :---: | :--- | :--- | :--- |
| **1** | **사용자 트래픽 변화율** | $S$ 및 $SWRI$의 직접적 입력 변수 | 시간당/일별 활성 사용자 수, 요청 빈도 (RPS) |
| **2** | **시스템 성능 지표** | $S$의 핵심 측정 항목 | 평균 응답 시간(Latency), 에러율(Error Rate), 시스템 가용성(Uptime) |
| **3** | **경쟁사 가격 변동** | $SWRI$에 대한 외부 시장 영향 분석 | 주요 경쟁사의 서비스 가격, 구독 모델 변화, 프로모션 활동 |
| **4** | **사용자 행동 로그 (Conversion/Retention)** | $SWRI$의 최종 결과 지표 | 사용자 참여율(Engagement Rate), 전환율(Conversion Rate), 이탈률(Churn Rate) |

각 변수에 대해 신뢰할 수 있는 데이터를 확보하기 위한 구체적인 소스 목록과 수집 방법을 제시합니다. (현재는 가상의 경로를 기반으로 계획을 수립하며, 실제 데이터 연동 시 해당 경로에 따라 실행됩니다.)

#### 변수 1: 사용자 트래픽 변화율

*   **데이터 소스 목록:**
    1.  **내부 로그 데이터:** 백엔드 서버 및 API 게이트웨이에서 수집되는 요청 로그 (Timestamp, IP/User ID, 요청 성공/실패 여부).
    2.  **프론트엔드 분석 데이터:** 웹/앱 세션 추적 데이터 (방문자 수, 활성 사용자 수).
*   **초기 수집 계획:**
    *   **방법:** 기존에 구축된 데이터 파이프라인(`sessions/...` 폴더 참조)을 통해 지난 7일간의 일별 평균 요청 수와 피크 타임 데이터를 추출합니다.

#### 변수 4: 사용자 행동 로그 ($SWRI$)

```json
  "value": "Float",                 // 실제 값
```

#### 1. 데이터 모델 정의 (Data Contracts)

```json
{
  "timestamp": "2026-05-22T14:30:00Z",
  "system_stability_S": 0.95,  // 0.0 ~ 1.0 사이의 안정성 지표 (내부 계산된 값)
  "revenue_metrics_SWRI": 15200.50, // 수익 지표 (내부 계산된 값)

    "code": "NONE",
    "message": "System is operating normally.",
    "reason": ""
  },
  "data_source_integrity": "OK" // 데이터 파이프라인의 무결성 상태
}
```

**B. `MetricQueryRequest` (지표 조회 요청)**

```json
    "start_time": "2026-05-10T00:00:00Z",
    "end_time": "2026-05-22T00:00:00Z"

```

#### 3. 데이터 흐름 및 Circuit Breaker 로직 상세 명세

##### A. 데이터 흐름 (Data Flow)

1.  **입력 단계 (Ingestion):** 외부 행동 로그(Instagram, YouTube 등) 및 시장 변동성 데이터가 `/api/v1/data_ingest`를 통해 시스템으로 유입됩니다.
2.  **처리 단계 (Processing):** 수집된 데이터는 내부의 데이터 파이프라인을 거쳐 `UserEventLog` 및 `SystemMetric` 테이블에 기록됩니다.
3.  **계산 단계 (Calculation):** 백엔드 로직은 이 로그와 메트릭을 기반으로 **상관관계 분석 전략**을 적용하여 $S$ (안정성)와 $SWRI$ (수익 지표)를 실시간으로 계산합니다.
4.  **출력 단계 (Reporting):** 최종적으로 계산된 $S$, $SWRI$, 그리고 데이터 파이프라인의 무결성 상태는 `/api/v1/status` 엔드포인트를 통해 프론트엔드로 보고됩니다.

##### B. Circuit Breaker 로직 (Resilience Logic)

Circuit Breaker 패턴은 외부 시스템(예: 외부 API 호출, 데이터 소스 연결)과의 통신 실패 시 시스템의 안정성을 보호하는 데 중점을 둡니다.

1.  **상태 정의:**
    *   **CLOSED (닫힘):** 정상 상태. 모든 요청을 허용하고 모니터링합니다.
    *   **OPEN (열림):** 오류 임계값 초과 시, 외부 호출(예: 데이터 수집)을 일시적으로 차단하고 즉각적인 실패 응답(HTTP 503 Service Unavailable)을 반환합니다. 유지보수 기간 동안 시스템 부하를 줄입니다.
    *   **HALF-OPEN (반쯤 열림):** 일정 시간이 지난 후, 제한된 수의 테스트 요청만을 허용하여 외부 시스템의 복구 상태를 확인합니다. 성공 시 CLOSED로 전환, 실패 시 다시 OPEN으로 전환합니다.

2.  **트리거 조건:**
    *   특정 데이터 소스(예: PayPal API 또는 행동 로그 DB)와의 연결 실패율이 **임계값 ($\theta$)**을 초과할 경우, Circuit Breaker는 `OPEN` 상태로 전환됩니다.
    *   데이터 파이프라인에서 발생하는 '사일런트 실패' (응답 없음, 타임아웃)가 감지될 경우, 즉시 CB를 OPEN으로 전환합니다.

3.  **로직 적용:**
    *   `/api/v1/data_ingest`와 같은 외부 의존성 호출 전에 반드시 Circuit Breaker 상태를 확인하여 연결을 시도할지 여부를 결정합니다.
    *   시스템 안정성($S$) 지표는 CB의 현재 상태를 직접 반영하도록 설계하여, 사용자는 시스템이 현재 '안정적인가'에 대한 명확한 신호를 받습니다.

Circuit Breaker 트리거 조건(Circuit Breaker Trigger Conditions)## 3.1 안정성 임계값($S$ Thresholds)# 시스템의 안정성을 기준으로 트래픽/상황에 따른 차단 기준을 설정합니다.$S_{CRITICAL} = 0.3$: 시스템이 심각한 불안정 상태일 때.$S_{WARNING} = 0.6$: 시스템이 주의가 필요할 때.$S_{SAFE} = 0.95$: 시스템이 안정적일 때.## 3.2 Circuit Breaker 작동 규칙(Rule Set)# **A. 트래픽 차단 (Traffic Isolation)**: $S < S_{WARNING}$ 일 경우, 모든 외부 API 호출을 일시적으로 차단하고 사용자에게 대기 메시지를 반환합니다.$B. 지표 기반 차단 (Metric-based Isolation)**: $SWRI$가 특정 임계값($SWRI_{CRITICAL} = 0.8$)을 초과하거나, $\text{Traffic\_Change}$가 급격히 변동할 때 시스템의 추가적인 리소스를 비활성화합니다.$C. 복구 전략 (Recovery Strategy)**: 차단된 상태에서 $S$가 $S_{SAFE}$ 이상으로 회복될 때까지는 트래픽을 대기열(Queue)로 전환하고, $S$가 특정 시간 동안 $S_{WARNING}$ 이하로 유지되면 자동 복구 시도를 시작합니다.$D. 로그 기록 요구사항(Logging Requirement)**: 모든 차단 및 복구 이벤트는 `system_status_log` 테이블에 상세한 원인 코드와 트리거 시점($timestamp$)을 기록해야 합니다.## 4. 기술적 구현 고려사항(Implementation Considerations)# **비동기 처리**: 외부 API 호출 시에는 반드시 비동기 패턴을 사용하여 지연 시간 문제를 최소화하고, 타임아웃(Timeout) 설정을 명확히 해야 합니다.$S$ 계산은 배치 작업으로 분리하여 실시간 요청에 부하를 주지 않도록 설계합니다.## **데이터 일관성**: $S$와 $SWRI$의 연산은 트랜잭션 격리 수준을 보장해야 하며, 데이터베이스 트랜잭션 내에서 동시에 업데이트되어야 합니다.$External\_Factors$는 외부 API로부터 가져오는 지연 시간과 오류를 고려하여 캐싱 레이어를 도입합니다.## **모니터링**: Circuit Breaker 상태(Open/Half-Open/Closed) 변화는 별도의 알림 채널로 실시간 모니터링되어야 합니다.
